# Spec coverage audit — index

How many properties does the bunny.net OpenAPI spec declare per
resource, and how many does our hand-written Rust struct model? One
row per resource; counts are summed across all (read shape, update
payload, create payload) tuples we model for that resource.

Generated by `hoppy-knowledgebase/scripts/run-spec-coverage-audit.sh`.
See [[../../iterations/iteration-43-openapi-gap-analysis]] for the
motivating audit and the per-bucket categorisation appended to
[[pull-zone]].

A companion report at [[fixture-coverage]] diffs recorded e2e fixtures
(`fixtures/<domain>/`) against the structs and specs — a third source
of truth showing what the API actually ships today. It confirms the
struct gaps surfaced here, and turns up a small amount of *spec lag*
(notably 6 undocumented fields in `videolibrary_get.json`).

## Totals

- **Total spec properties across modelled schemas:** 774
- **Total struct fields across modelled types:** 291
- **Total missing from struct (the systemic gap):** **503**
- **Total casing mismatches:** 77 (mostly camelCase ⇄ PascalCase between Shield/Stream APIs and our PascalCase-rename serde defaults — not coverage gaps, but worth a separate sweep)
- **Total reverse gaps (in struct, not in spec):** 20 (likely stale or schema-renamed)

## Caveats

- Counts include `read-shape`, `update-payload`, and `create-payload`
  per resource. This *over-counts* "real" gaps when the same field is
  missing from all three (e.g. `EnableTLS1` appears in both
  `PullZone` and `UpdatePullZone` audits).
- The audit script PascalCases Rust field names; APIs that use
  `camelCase` (Shield, Stream V2) consequently land most fields in
  the "casing mismatches" column rather than the gap column. Treat
  those reports as **coverage-likely** until a casing-aware sweep is
  done.
- `container-app` has no spec checked in under `specs/` — see the
  resource file for follow-up.
- Schemas with `allOf` composition are flattened by the script; deeper
  composition (`oneOf`, `discriminator`) is not handled and surfaces as
  a TODO in the per-resource file.

## Next-iteration recommendation

Pull-zone alone accounts for the bulk of the systemic gap and is the
only resource where users *can't reach the API surface from the CLI
at all* (the dashboard exposes ~45 toggles we don't). Land the
`security / compliance` bucket in iter-44; sequence the rest off the
[[pull-zone]] severity grouping.
